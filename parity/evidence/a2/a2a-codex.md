## 3. Mechanism choice

- **Package, skills, and bundled agents:** Pi package declarations are used for extensions and skills; the package-relative agent loader is necessary because Pi 0.87.1 has no native package `agents` resource. Its package/user/trusted-project merge is a reasonable documented extension adapter.
- **Task/subagents and run supervision:** Spawning a local Pi CLI child with a separate transcript, explicit tool list, selected extensions, abort/wait state, and `--mode json` follows the official subagent extension example. Pi has no native Task/Await/Shell or durable background-process service to replace it. Parallel fan-out is intentional and per-run state/retry claims are keyed and tested, but `Task.executionMode = "parallel"` shares the mutable run-store registries and is a literal exception to Pi’s sequential-mode guidance (Finding 6).
- **Sticky mode and goals:** `appendEntry`, active-branch reconstruction, `before_agent_start`, `agent_before_settle`, `sendMessage`, and status APIs are the best documented mechanisms for session/branch-local state and recurring reminders. No native sticky-mode or goal API was found. The mode reminder is additive rather than a full system-prompt replacement.
- **Questionnaire and todos:** The questionnaire follows Pi’s official example and documented TUI/RPC/headless paths. Todo details are the right branch-aware storage, with a TUI-only list screen and sequential mutation mode.
- **Loop/wake notifications:** A managed runner plus Shell sentinel, notification, and Await is an extension adapter; Pi has no native recurring wake scheduler. It cannot promise survival of host shutdown.
- **Guards/security:** `tool_call` blocking is the documented preflight mechanism, but the tool hook is a model policy gate, not OS isolation. A git worktree is not a substitute sandbox. Shell-capable tools need explicit threat-model language.
- **Model selection/config:** The extension-owned `pstack-agents.json` is preferable to undocumented Pi `settings.json` keys and uses `getAgentDir()`. The producer instructions and fail-open parse branches still need alignment (§5).

## 5. Ranked findings

1. **P1 — Model-scope enforcement can silently disappear.** `loadModelScope()` treats every file-read error as “no policy” (`extensions/pstack-agents/agents.ts:345-352`), and `parseModelScope()` returns `undefined` when a present `modelScope` is not an object (`:287-289`); `modelMatchesScope(undefined)` allows every model (`:301-303`). Separately, setup-pstack writes literal `~/.pi/agent/extensions/pstack-agents.json` (`skills/setup-pstack/SKILL.md:75`) while the reader uses `getAgentDir()`, so a configured `PI_CODING_AGENT_DIR` misses the policy. **Smallest fix:** use the configured agent dir in the skill; ignore only `ENOENT`; throw on other read errors and on a present malformed policy key. Add tests for unreadable file, wrong-shaped key, and non-default agent dir.
2. **P1 — “Server-side secret” is available to bot tools.** `make-bot-ui` stores the credential under the bot directory and passes it into the Pi process environment (`skills/make-bot-ui/SKILL.md:19-22,44-54`). The bot can use `read` on the known `secret` path, and a shell-capable tool can read the inherited environment (`extensions/pstack-agents/runner.mjs:349-363,448`; `runs.ts:568-574`). Pi’s `--tools` allowlist can include built-in, extension, or custom tools (`cli.md:118-125`), but allowing `read` for `routine.md` does not restrict it to that file. Thus “never in the prompt” does not keep the credential from the model. **Smallest fix:** keep the secret outside the Pi-accessible bot directory and process; have a server-side narrow tool/proxy consume it without returning it. Otherwise use an OS-enforced file/process boundary, not prompt instructions.
3. **P2 — Installed-skill write guard is bypassable through commands.** The guard blocks protected paths only for built-in `write`/`edit`; Bash handling is for background polling, and custom `Shell` is unrestricted (`extensions/pstack-guards.ts:298-332`; `pstack-agents/runner.mjs:448`). A model can write the same skill through shell redirection. README’s “guards that block edits to installed skills” (`README.md:38`) overstates coverage. **Smallest fix:** describe it as a built-in-tool advisory gate, not write isolation; if comprehensive prevention is required, remove shell-capable tools or enforce it outside the model process.
4. **P2 — `SubagentAwait` omits the completed child’s final message.** Cursor’s completed result carries `final_message` (CLI bundle descriptor `SubagentAwaitComplete`); Pi’s `SubagentAwait` returns only status and transcript path (`pstack-agents/index.ts:538-571`), although `store.finalOutput(id)` is available (`runs.ts:795-797`). **Smallest fix:** include a bounded final-output excerpt and the transcript path when terminal, matching the foreground Task result.
5. **P2 — Shell notification parity is lossy and potentially unbounded.** Cursor’s structured notification includes a reason and optional debounce/notification limit; Pi accepts only a regex string and reconciles every matching line into a notice (`pstack-agents/index.ts:65-74`; `runs.ts:483-500`). A noisy pattern can enqueue many turns. **Smallest fix:** accept the structured object, implement its cap/debounce, or explicitly document the Pi-only string shorthand and impose a safe notification limit.
6. **P2 — Failed/background Task attempts can be missing from parent usage totals.** A failed status throws before usage is claimed (`pstack-agents/index.ts:334-340,538-571`). A background launch returns before usage exists (`:350-357`), and completion notifications do not claim/attach it (`:215-240`); usage reaches a parent tool result only if a later terminal, non-failed Task/Await call claims it. This contradicts `README.md:51`’s unconditional “once for each run attempt.” **Smallest fix:** persist failed/background usage in parent-visible accounting, or narrow the documented promise and require an Await after completion.
7. **P2 — Task’s parallel execution shares mutable run-store state.** `Task` sets `executionMode: "parallel"` (`pstack-agents/index.ts:579-589`), while Task/Shell/Await calls share `runStore` maps/sets and an observer (`:109-112,585-620`; `runs.ts:390-401,445-457`). Per-run keys and retry tests mitigate collisions, but the docs say to serialize tools sharing mutable state. **Smallest fix:** isolate per-run mutable state or add explicit synchronization and cross-tool concurrency tests; switching to sequential would change the specified parallel fan-out.
8. **P2 — Local worktree wording still risks implying isolation.** The package correctly says execution is local, but keeps `environment: "cloud"` and calls the worktree “isolated” (`skills/poteto-mode/references/pi-runtime.md:19`; `README.md:50`). `git worktree` does not constrain shell filesystem/network/credential access. **Smallest fix:** call this a separate local worktree, explicitly say it is not a sandbox, and retain `cloud` only as a compatibility token.
9. **P3 — Unsupported Task machine fields remain in the accepted schema.** `machine` and `cloud_requested_environment_build_id` are `Type.Optional(Type.Unknown())`, then rejected (`pstack-agents/index.ts:44-57`; `agents.ts:395-399`). README documents the refusal (`README.md:50`), so this is not hidden, but callers still receive a schema that advertises unsupported inputs. **Smallest fix:** remove both from the model-facing schema/type, or keep a clearly marked compatibility shim outside the advertised Pi schema.
10. **P3 — Tests depend on the parent Task environment.** With this audit running as `pstack-general`, `npm test` initially failed four `fp.test.ts` tests because `pstack-mode.ts:54` suppresses registration for non-`poteto-agent` children. Clearing inherited `PSTACK_AGENTS_*` made all 126 tests pass. The package test command does not isolate those variables (`package.json:52-57`). **Smallest fix:** unset pstack child markers in the test script or set/restore them explicitly in tests that exercise the top-level extension factory.
11. **P3 — Package-plan tarball predicate is narrower than the shipped allowlist.** The plan says `npm pack --dry-run` should contain only Pi manifest resources plus README/license/notice/changelog (`parity/PACKAGE-PLAN.md:12`), while `package.json:31-35` also ships `docs/`, `automations/`, and `assets/`; the dry run lists 182 files. These extras may be intentional (README links the guide), but the predicate should name them or the allowlist should exclude them. **Smallest fix:** update the plan’s predicate to enumerate the intentional extras.
