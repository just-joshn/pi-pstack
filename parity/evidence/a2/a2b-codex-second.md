## 3. Mechanism choice

| Package behavior | Mechanism used | Best documented Pi mechanism? |
|---|---|---|
| Agent definitions and `Task` child sessions | Package-root Markdown loader plus an extension-managed Pi subprocess with transcript/run store | **Yes, as a custom adapter.** Pi has no package `agents` resource or built-in Task tool; the official subagent example uses an extension-owned agent loader. `streamSimple()` is for nested model calls, not a separate Pi child with tools, skills, and its own session. |
| Background Shell, waits, notifications, interruption | Custom TypeBox tools and run supervisor; `pi.sendMessage()` wakes the session | **Yes, as an extension adapter.** Pi exposes process/session primitives but no native Cursor Shell/Await contract or durable task registry. |
| Goal state and continuation | Branch-local custom entries plus `agent_before_settle` | **Yes.** This is the documented state and continuation boundary; Pi has no native goal API. |
| Sticky `poteto-mode` | `session_start`/`session_tree` branch reconstruction, `before_agent_start` custom messages, `/poteto`, and status UI | **Yes.** Pi has no sticky-mode or skill reminder frontmatter. A structured prompt section is another documented option, but the extension does not replace the whole prompt. |
| AskQuestion and TodoWrite | TypeBox `questionnaire`/`todo` tools; TUI custom UI, RPC dialogs, headless text fallback; result details for branch state | **Yes.** These follow the official questionnaire/todo examples and supported mode-specific UI APIs. |
| Shell loop guard and child playbook restrictions | `tool_call` blocking | **Yes for a policy hook, not for containment.** This is the documented interception point. A separate OS/container boundary is required for security. |
| Model allowlist | Extension-owned `extensions/pstack-agents.json` | **Yes.** The loader follows the extension-specific configuration-file pattern from the sandbox example; it does not invent a Pi settings key. |
| Run records and exactly-once claims | Per-session/per-run external files with atomic writes and exclusive claim files | **Yes.** Detached processes need shared durable state; the in-process `withFileMutationQueue()` cannot coordinate a child process. |
| `environment: "cloud"` | Local managed Git worktree | **Only for source-tree separation.** Pi has no native remote/cloud Task mechanism. No worktree adapter can reproduce remote execution or its security boundary without an actual remote sandbox/backend. |

## 5. Ranked findings

1. **P1 — Local worktree is still described as cloud/isolated execution.** `skills/poteto-mode/playbooks/multi-phase-plan.md:75`, `orchestrate.md:17`, and `shipping.md:7` call the local worktree a cloud VM, isolated, or equivalent to Cursor cloud. The child Pi and Shell run locally with the host process permissions (`extensions/pstack-agents/runner.mjs:324-378,439-449`; `worktrees.ts:191-232`); Pi security explicitly says a working directory/worktree is not a security boundary (`docs/security.md:3-21`). **Smallest fix:** replace those phrases everywhere with “separate local Git worktree; same host account/permissions, not a sandbox.” Reserve “cloud equivalent” for a real remote backend.

2. **P2 — Arena instructs an unsupported `Task.output` argument.** `skills/arena/SKILL.md:35` backticks `output` as a Task field, but `TaskParameters` rejects additional properties and has no output member (`extensions/pstack-agents/index.ts:44-60`); Cursor's Task proto has no output either. **Smallest fix:** say to put the path in each Task's `prompt`, not in the tool arguments, and add a schema-level probe for the exact call shape.

3. **P2 — `npm run check` fails in a standard non-poteto Task child.** `pstack-mode.ts:54` intentionally returns early when `PSTACK_AGENTS_DEPTH` is set and the agent is not `poteto-agent`; the direct extension tests in `parity/probes/fp.test.ts:302-337` do not isolate those variables. With this task's inherited `PSTACK_AGENTS_DEPTH=1`, four tests failed. `env -u PSTACK_AGENTS_DEPTH -u PSTACK_AGENTS_AGENT npm run check` passed. **Smallest fix:** clear/restore these variables in the probe setup or run those probes in a clean subprocess.

4. **P2 — setup and transcript instructions ignore `PI_CODING_AGENT_DIR`.** `setup-pstack/SKILL.md:8,18,39,75` writes/reads `~/.pi/agent`; `pi-runtime.md:51-59,65,85` also hard-codes paths, while the runtime loader correctly uses `getAgentDir()` (`agents.ts:345-359,482`). With a custom agent dir, the model block/modelScope may be written somewhere the extension never reads, and transcript guidance can target the wrong store. **Smallest fix:** use `<agent-dir>`/`PI_CODING_AGENT_DIR` with the documented default in every actionable instruction and script.

5. **P2 — README overstates background usage accounting.** A foreground terminal result or explicit terminal `SubagentAwait`/`Await` claims usage once (`index.ts:339-340,570-571`; `runs.ts:801-826`), but an interactive background completion is only a custom message and has no usage (`index.ts:215-242`). Tests explicitly expect a background Task receipt to have no usage until Await (`index.test.ts:530-559`). **Smallest fix:** qualify `README.md:51` to say background usage enters totals only when a terminal tool result is collected, and instruct callers to await; alternatively provide a usage-bearing completion result path.

6. **P2 — Parity audit's “0 unjustified” is not semantic assurance.** The full-audit script accepts any nonempty reason/reference and counts every reason except the literal `UNJUSTIFIED` as justified (`parity/full-audit.mjs:25-52,96-115`). Its 98.91% score is lexical Jaccard coverage, 0.01 percentage point above the floor, with 54 gaps; it cannot validate tool-call correctness. The 25-row sample found the invalid `Task.output` instruction and false cloud-equivalence claims. **Smallest fix:** label the current result as lexical coverage/inventory completeness, add contract probes against registered TypeBox schemas, and require a human semantic review for justifications.

7. **P3 — Unsupported remote Task fields remain callable.** The schema accepts `machine` and `cloud_requested_environment_build_id`, then always throws (`index.ts:44-60`; `agents.ts:396-399`). README discloses the rejection, but A1 fix 11 (“remove or implement”) was not completed. **Smallest fix:** remove those fields from the Pi schema/tool instructions, or keep them explicitly marked unsupported in the tool description and test the error.

8. **P3 — Shell parity is intentionally narrower than Cursor's proto.** `output_notification` is a regex string, not the Cursor nested config; reason/debounce/notification limit and approval/sandbox/output-threshold fields are absent (`index.ts:65-74`; Cursor `ShellArgs`/`ShellOutputNotificationConfig`; `round3-decisions.tsv:50`). The sentinel-only reduction is logged, so this is a known limit rather than a hidden regression. **Smallest fix:** if strict parity is required, accept and implement the nested config; otherwise keep the reduced contract prominent in the runtime guide and README.
